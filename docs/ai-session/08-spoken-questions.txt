  ## 5. The design

  Everything in this section is Claude's call, for the owner to check.

  ### 5.1 The Speak button

  - The form gains one button, **Speak**, beside Ask. The HTML carries it
  hidden. The script shows it only when the browser offers speech recognition
  under either name (`SpeechRecognition`, or the prefixed
  `webkitSpeechRecognition` that Safari uses). In any other browser the page is
  today's page.
  - One press starts listening, and the button reads **Stop**. Listening ends
  when the analyst pauses, presses Stop, or the browser reports a problem. Then
  the button reads Speak again.
  - Settings: English, set explicitly (`lang` "en-US"; MDN: "Setting this
  explicitly is the recommended best practice"). One utterance per press
  (`continuous` false: "at most one final result"). Words shown while they are
  heard (`interimResults` true). Where recognition runs is left to the browser
  (`processLocally` stays false).
  - Pressing Stop puts the page back to normal at once, without waiting for the
  browser. So Ask can never stay stuck.
  - A spoken question costs what a typed one costs. The speech step is free to
  us, and only Ask reaches the model.

  ### 5.2 Misheard words: seen, fixed, then sent

  - **Seen.** The words go into the question box and nowhere else, and they
  appear while the analyst speaks. Text already in the box stays. The spoken
  words are added after it with one space. The result is cut at 2,000
  characters, because the browser does not apply the box's limit to text a
  script writes (section 3).
  - **Fixed.** When listening ends, the box is an ordinary text box again, with
  the cursor at the end. The analyst corrects a word by typing. Pressing Speak
  again adds more. While listening, the box is read-only, so the next result
  cannot overwrite a correction half made.
  - **Then sent, by the analyst.** Speech never sends. Only Ask and Enter send,
  as today. While listening, Ask is disabled, and Enter then does nothing (line
  263), so words the recogniser may still change cannot be sent. One trap: today
  `setWorking` alone sets Ask's state (line 219). The builder makes one rule,
  "disabled while working or listening". Otherwise an answer that arrives
  mid-speech re-enables Ask.
  - **Never corrected by the page.** No matching against hub names. A wrong
  guess by our code would look as right as a wrong guess by the recogniser.
  - **What already stands behind it.** The conversation shows the question
  exactly as sent. Code writes the tables, and they name their hubs. A city with
  no hub is answered "Out of scope" (evaluation case 11). None of that catches
  one real hub heard as another, which is why the analyst reads first.
  - **Not used: word hints.** Browsers can take a list of likely phrases
  (`phrases`). Chrome has it from 142 and Safari not at all (S3), and a
  recogniser without it fails the whole request with `phrases-not-supported`
  (S4). It is the next step only if the owner's run in 5.6 shows hub names
  misheard.
  - **How well it hears is unknown.** UNVERIFIED until the owner's run in 5.6.
  It depends on the speaker, the microphone and the room.

  ### 5.3 What the page tells the analyst

  A fixed line under the box, shown whenever Speak is shown. The exact words are
  the builder's. It says three things:

  1. The browser, not this site, turns the speech into text.
  2. The browser may send the audio to its maker to do that. Chrome sends it to
  Google.
  3. This site receives only the text, and only when Ask is pressed. Check the
  words first, hub names above all.

  A second line, in the pattern of the page's "Working" line and announced to
  screen readers, says what is happening: listening; then "check the words, then
  press Ask"; or the problem from 5.4. The README repeats the three points
  browser by browser, with what is UNVERIFIED (section 3: Safari and Edge).

  - **What the browser requires.** Consent, which it asks for in its own prompt
  the first time Speak is pressed. A page on HTTPS or on this machine's own

  `http://127.0.0.1:8000`. The page starts listening only from the button's

  - **The sign-in cannot get in the way.** The page calls the browser, and the

  public site in 5.6 confirms it.
  - **No header blocks it** on the replies measured (section 3). We add none.

  browser use the microphone (UNVERIFIED), and whether Chrome asks again on

  ### 5.6 How it is checked

  **By tests,** with no browser, no microphone and no model:

  - Two functions written to stand alone, and run in Node as `boldOnly` is
  (skipped when Node is missing). The first joins the box's text and the heard

  ## 3. Questions only the owner can answer

  Blind spots first (things a builder about a year in would likely not ask):

  1. **The audio leaves the machine.** In Chrome it goes to Google (Chrome's own
  source). The page never touches it, so nothing in our code shows this. Is a
  notice enough, or must audio stay on the device? On-device adds a
  language-pack download step, works only in Chrome 139+ and Firefox 160+
  desktop, and Safari cannot be forced.

  it but only on-device, and by the specification a plain start fails until the
  page installs a language pack. Edge's has broken (network errors, spring
  2026). So which browsers must work is the owner's call: the demo browser, and
  Firefox yes or no.

  come out right, and it varies by speaker, microphone and room. What result of
  the 16-question run drops the feature? Better fixed before the run. My
  proposal: more than 2 of 16 wrong.

  voice be shown live? If yes, one rehearsal in the same setup.

  real voice work would reorder priorities (spoken answers, on-device).

  ## 3. Gaps and contradictions in the design

  1. **Late events after Stop (sections 5.1, 5.2).** Stop restores the page "at
  once", but the design does not say what happens to a result that arrives after
  that. It would overwrite the analyst's correction. The plan ignores every
  event from that recognition and calls `abort()` (decision 2; Review Focus 3).
  2. **The `restore()` race (section 5.2 trap; `index.html:214-216`).** The
  design expects speech to go on while an answer is coming. If that answer
  fails, `restore` fills an empty box, and the next result erases it. The plan
  disables Speak while an answer is coming. The one rule for Ask is still built.
  3. **The forbidden-call list (section 5.6)** leaves out `dispatchEvent`, which
  can fire the form's submit. The plan adds it.
  4. **"The served page read as text, as `tests/test_container.py` reads
  `.dockerignore`" (section 5.6)** mixes two methods. The plan reads `PAGE`, the
  same file the server sends (`app.py:29`, `:83-84`).
  5. **Section 6, step 4 against `CLAUDE.md:35`.** The deploy push "must not
  carry `[skip render]`", but every build commit carries it. One push holding
  both kinds gives an unknown result. The plan uses two pushes, each with a
  check first.
  6. **Browser caching after the deploy (section 5.6, step 7).** The page is
  sent with no Cache-Control, so the owner may see the old page. The plan adds a
  reload note.
  7. **Section 8, question 4.** "The notice leans harder" has no words. The plan
  writes them.
  8. **Section 5.6** says "a box that does or does not end in a space". The plan
  generalises this to any whitespace.
  9. **Section 5.6 asks the tests to find "the notice's three points".** The
  plan pins the exact notice instead, compared with whitespace collapsed.
  10. Not a contradiction, but worth knowing: goal 3 ("typing is untouched")
  sits beside the design's own choice of a read-only box while listening. The
