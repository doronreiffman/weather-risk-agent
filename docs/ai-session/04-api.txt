⏺ Answered Claude's questions:
  ⎿  · When the agent can't give an answer, what HTTP code should the chat 
     endpoint send? Today it returns a reply with status "error" and a plain 
     message. The causes are: a second message on a conversation still being 
     answered, the model unreachable or timed out, the model declining, or the 
     answer failing validation twice. The JSON body is the same reply object 
     under every option. → 409 busy, 502 others (Recommended)
     · What should the chat endpoint do with a conversation id the server 
     doesn't know? This happens mainly after a server restart, when the open 
     page still holds the old id. As built, the agent quietly starts a fresh 
     conversation under that id, so a follow-up like "and which is the least 
     exposed?" gets answered with no memory of the first question. → what's the 
     practical difference between 1 and 2?
     · How should the page show the model's Markdown? In the two saved 
     evaluation runs, the only Markdown the model wrote was bold (28 of 38 
     verdicts, e.g. **High**). No lists, links, italics or line breaks appeared.
     → Bold only, in the page (Recommended)
     · Should one message get an overall time limit? Each model call already 
     gives up after 60 s with one retry, but a message can make up to 6 calls. A
     slow API could keep the page on "working" for about 12 minutes, with the 
     conversation locked all that time. The longest message in the two saved 
     evaluation runs took 8.7 s, and the median about 5 s. → 90 s per message 
     (Recommended)
