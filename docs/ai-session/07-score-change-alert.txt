  === BEGIN docs/ALERT_DESIGN.md ===

  # The score-change alert: design

  **Grade: demo.** The plan's "interview take-home prototype" (`docs/PLAN.md`,
  top). One command and one scheduled job, checked by tests and a few real runs.
  Not production: one destination, no history service, nothing watching the job
  itself.

  Status: **proposed on 2026-11-25, for the owner's approval.** Queue item q8.
  "Read" means the words were read that day on the page named. "Measured" means
  run that day with this repository's code and data. Anything not checked is
  marked UNVERIFIED.

  ## 1. Why, and for whom

  The assignment: "Bonus: a scheduled or webhook-triggered alert when a hub's
  risk score changes". It also says: "A narrow scope done well is better than a
  broad scope done shallowly." Of the two bonuses left, the owner chose this one
  and dropped voice, because the alert serves the narrow scope better
  (2026-11-25).

  - **In the story,** the analysts have defended a ranking to their boss. If the
  data behind it moves, they should hear which hubs moved and by how much.
  - **In reality,** the reviewers should see the alert without the owner: the
  job, its run history and one example message, all in the public repository.

  One thing comes first. The score covers ten finished years, 2016 to 2025, plus
  FEMA's long hurricane record (`config/scoring.toml`,
  `src/wra/ingest/__init__.py`), and a refresh asks for the same years again. It
  moves only when a source corrects past records, FEMA publishes a new release,
  the period is moved forward, or the weights or counting rules are edited. So
  an honest alert will nearly always say "no change". Measured: a fresh fetch
  one day after the stored one changed none of the 60 figures, 12 ranks and 12
  bands. That gives the design two jobs: make "no change" believable, and give
  the demo a clearly labelled way to fire (5.6).

  ## 2. Goals, non-goals, anti-goals

  Goals, most important first:

  1. **A real change reaches a person,** in words they can act on, with every
  figure taken from the scoring code.
  2. **"No change" can be believed.** A run that could not check fails in plain
  sight. It never reads as "no change".
  3. **A reviewer can see it work** without running anything.
  4. **Nothing else moves.** The site, the local commands and the evaluation
  behave as today. No model, no paid call.

  Non-goals: alerts about weather happening now (out of scope since the
  interview's answer 8, so the Weather Service's live feed that plan section 4.3
  kept for this bonus is not used); saying which individual warnings moved a
  figure; a chat or email message of our own; a history of scores beyond git;
  tests run on every push; watching anything but the overall ranking.

  Anti-goals (a failure even if everything else works):

  - A false alarm: an issue for a failed fetch or a changed time stamp, or a
  demo that reads as real.
  - The alert changes what it watches: the job pushes, the site restarts, or the
  saved copy moves with no person involved.
  - The same change is reported every week.
  - A figure in the message that the scoring code did not produce.

  ## 3. Constraints

  **The project** (checked in the code):

  - No score is stored: the database's seven tables hold none

  ## 4. Approaches considered

  **Where the alert lands** (the owner's pick, 2026-11-25):

  | Destination | New secret | Who sees it | To build |
  |---|---|---|---|
  | **An issue in the public repository, opened by a scheduled GitHub job
  (chosen)** | None: the job's own token | Anyone who opens the repository;
  people watching it are notified | A workflow file |
  | A chat-channel webhook, Slack-style | The webhook's address | The channel's
  members; reviewers only on a shared screen | The same job plus the secret |
  | Terminal and a file only | None | Whoever runs the command | Least |

  The issue wins because a reviewer sees it without the owner, it needs no
  secret, and it can be closed when the change is dealt with. The third option
  survives inside it: the same command runs in a terminal.

  **Where the saved copy lives** (Claude's call):

  | Option | Verdict |
  |---|---|
  | **A committed file that only a person's command changes (chosen)** | It
  means "the ranking as last reviewed". The job never pushes, so it cannot
  restart the site. Git's history of the file is the history of the score. |
  | The job commits the new scores itself | Rejected. Each push redeploys the
  site, and a bad fetch would become the baseline with nobody looking. |
  | The job opens a pull request with the refreshed data | The natural next
  step, not built. "By default ... workflows are not allowed to create or
  approve pull requests." |
  | GitHub's storage for run files | Rejected. Reviewers cannot see it, and such
  files "are retained for 90 days". |

  ## 5. The design

  Everything in this section is Claude's call, for the owner to check.

  ### 5.1 What counts as a change

  The alert compares the overall ranking of all twelve hubs, as the `rank_hubs`
  tool returns it and `wra rank overall` prints it: for each hub the overall
  figure, the four hazard figures, the rank and the band; for the ranking, its
  one confidence label. That is 85 values. Any difference is a change. There is
  no threshold, because the message says how big each change is.

  - Figures are compared as the ranking shows them, to two decimals. A movement
  too small to show is not a change; one that crosses a rounding edge is.
  Measured: with the hurricane weight at 6, Columbus moves from 0.99 to 1.00 and
  from Low to Moderate, while each of its hazard figures shows the same two
  decimals. The message must cope with that.
  - A hub whose rank changed only because others passed it is listed apart. A
  hub added or removed is a change.
  - The inputs are saved too: weights, period, band cut-offs, FEMA's release
  name, the fetch date. They never trigger an alert alone. When scores have
  moved, the message says which inputs differ. A moved period shows up through
  the figures it moves.

  ### 5.2 The saved copy

  One committed file, `data/reviewed_scores.json`, one hub per line so a diff
  reads easily.

  - Only `uv run wra alert --accept` writes it. A person runs that and commits
  the file with the change that caused it. The job reads it and never writes it.
  - A test ties it to the repository: scores from the committed raw responses
  and config must equal the committed copy. A weight edited, or `data/raw/`
  refreshed, without `--accept` fails `uv run pytest`.
  - While a real change waits for review, the job finds the same difference each
  week. 5.5 stops the repeats.

  ### 5.3 The command

  `wra alert` compares and prints. No network, no model, no key.

  - `uv run wra alert` prints one "No change" line, or the issue's title and
  body. This is the dry run: the message is read and tested without GitHub.
  - `--accept` writes the saved copy. `--demo` is in 5.6. The two together are
  refused.
  - For the job, it also writes the title and body to files and tells three
  results apart: no change, change, could not compare. A failure must never look
  like "no change".
  - The logic is pure functions: take a snapshot from the tool result, compare
  two, write the message, work out a change id (a short hash of the
  differences). None of it talks to GitHub, so `src/wra/ingest/fetch.py` stays
  the only module that uses the network.

  ### 5.4 The job

  One workflow file, `.github/workflows/score-alert.yml`.

  - **When:** weekly, at a minute away from the top of the hour; and by hand,
  with one tick-box input, `demo`.
  - **What it may do:** `contents: read` and `issues: write`. Nothing else, so
  it cannot push.
  - **Steps:** check out; install `uv` and the project; `uv run wra ingest
  --refresh` (a demo run builds from the committed data instead, 5.6); `uv run
  wra alert`; on a change, 5.5. The result line goes on the run's summary page,
  so "No change" is read without opening a log.
  - **Where:** on GitHub's throwaway machine. The fetched files are discarded
  with it. The site is never touched.
  - **When it cannot check:** a failed fetch or a stopped build fails the run.
  No issue is opened. GitHub's notice of a failed scheduled run goes to "the
  user who initially created the workflow", if that user has such notices on.

  ### 5.5 The issue

  The job opens it with `gh`, which "is preinstalled on all GitHub-hosted
  runners", under the label `score-change`.

  - **Duplicates.** The body ends with the change id. If an open issue with the
  label carries the same id, the job opens nothing and the run's summary names
  that issue. A different difference is a new issue. The job never edits or
  closes one.
  - **Wording.** Code writes all of it: the changed hubs, the rank-only hubs,
  the confidence label, the inputs that differ, and what to do next.

  An example with the demo's real figures (measured; the layout is the
  builder's):

  > **[DEMO] Hub risk scores changed: 9 of 12 hubs, 3 changed band**
  >
  > **This is a demonstration, not a real change.** The official scores have not
  moved. For this run only, the hurricane weight was 10 instead of 5, on the
  data committed in the repository.
  >
  > | Hub | Rank | Disruption days a year | Band | What moved |
  > |---|---|---|---|---|
  > | Miami (MIA) | 8 → 1 | 1.85 → 3.37 | Moderate → Very high | Hurricanes 1.52
  → 3.05 |
  > | Houston (IAH) | 7 → 3 | 1.96 → 2.88 | Moderate → High | Hurricanes 0.92 →
  1.84 |
  > | Columbus (CMH) | 11 | 0.99 → 1.02 | Low → Moderate | Hurricanes 0.03 →
  0.06 |
  > | (six more rows) | | | | |
  >
  > Rank only, own figures unchanged: Minneapolis 1 → 2, Denver 3 → 5, Kansas
  City 4 → 6.
  > This says that figures differ, not why. A hiccup at a source can look like a
  change, so run the job again first.

  ### 5.6 The demo

  A manual run with `demo` ticked, or `uv run wra alert --demo`, compares the
  saved copy with the ranking under **the hurricane weight doubled**, from 5 to
  10.

  - It uses the what-if `rank_hubs` already has, so no scoring code is added and
  no file is edited. Evaluation case 7 expects the chat to make the same tool
  call.
  - It fetches nothing. So it cannot fail on a source's bad day, and the laptop
  prints the same text as the issue.
  - The title starts with `[DEMO]`, the first line says the official scores have
  not moved, and the change id is marked too, so a demo never hides a real
  change.
  - The honest path is shown by a manual run without `demo` and by the scheduled
  runs: a real fetch, "No change", no issue.

  ### 5.7 How it is checked

  **By tests,** with no network and no GitHub:

  - The comparison and the message on hand-built snapshots: no change, one
  figure, a rank swap, a band crossing, the Columbus rounding case, rank-only
  hubs, the confidence label, a hub added, inputs that differ. The same
  differences give the same change id.
  - The command on the committed data: `wra alert` says "No change"; `--demo`
  gives the title above; `--accept` reproduces the committed file; `--accept
  --demo` is refused; a missing saved copy is a plain error.
  - The workflow file read as text, as `tests/test_container.py` reads
  `.dockerignore`: `contents: read` and `issues: write` only, and no `git push`.

  **Only by a real run on GitHub,** on the owner's go, since it means a push:

  - GitHub accepts the workflow file, the project installs there, and the three
  data services answer GitHub's machines. UNVERIFIED until then.
  - GitHub's Linux machine computes the laptop's figures: the run without `demo`
  says "No change", and the demo issue's text equals the laptop's.
  - The token opens the issue, a second demo run opens nothing, the owner is
  notified, and a scheduled run appears at its time.

  The documents follow the build: a README section and a line in the reviewers'
  front door, ARCHITECTURE, one DECISIONS entry, PLAN Deviations.

  2. **The `workflow` scope.** The main session checks whether the personal

  If it is missing, the owner runs `gh auth refresh -h github.com -s workflow`
